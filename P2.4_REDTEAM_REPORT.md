## Executive summary

The P2.4 attack harness reported 23/25 attacks detected going in. That number was optimistic in both directions: it undercounted real protection (nothing on the production write/read path was verified at all) and overcounted it (two of the core verifiers it called don't actually do what their own doc comments claim). A full pass — manual review, then a six-dimension adversarial multi-agent sweep with independent refutation of every claim — found a critical authentication bypass in the Merkle verifiers themselves, a complete integrity bypass in the agent's WAL sidecar, three crash bugs in the untrusted-HDF5 parser, and two places the harness's own "detected" column didn't mean what it said.

All of it is fixed, tested, and pushed to `main` as of this report, except two items that turned out to be deliberate, disclosed design tradeoffs rather than bugs — covered in Open Items below rather than silently changed.

## Method

Two passes. First, a manual read of the harness and every verifier it calls, checking whether each "detected: yes" would survive a *directed* adversary rather than the naive one the test constructs. Second, a six-agent adversarial sweep (`Workflow`) across distinct surfaces — Merkle soundness, signatures, AEAD/filters, agent persistence, untrusted parsing, harness honesty — with every finding independently re-verified by a second agent instructed to try to refute it, not confirm it. The sweep ran across three sessions interrupted twice by usage limits; resuming replayed completed work and only re-ran what had errored.

Every "confirmed" verdict was re-checked by hand against the actual file and line before any fix — not treated as ground truth. Two findings turned out to already be fixed by an earlier commit in this same engagement, and the re-verification caught that; they're not counted twice below.

## Findings

### Merkle verifiers never chained leaves to the root
**Critical · Fixed** · `clawhdf5-format/src/merkle.rs` — `verify_dataset`, `verify_chunk`

`verify_dataset`'s doc comment claims it "rebuilds the entire Merkle tree from scratch." It didn't — `reconstruct_tree` only deserialized the on-disk companion-node blob, and the function then compared a live chunk's hash against the *stored* leaf at that index, and the stored root against the attribute's root — both values read out of the same untrusted blob. Nothing ever verified leaves actually hash up to the root via `hash_pair`. `verify_chunk`, the O(log N) per-chunk check, had the identical gap: it never read a sibling or touched the root at all.

An attacker with write access to the chunk data *and* the companion-node blob could patch a chunk and its corresponding stored leaf, leave the root untouched, and pass both functions — including the signed-dataset rollback-recovery gate (`verify_restored_dataset`), reachable through `clawhdf5-secure-demo`'s actual restore path.

**Fix:** Both functions now rebuild from live, freshly-hashed leaves (padded with the write side's own null-sentinel scheme) and compare an independently re-derived root — what the doc comments always claimed. New regression tests reproduce the exact bypass and confirm it's closed; all 6 secure-demo stages, the full format suite, and the harness still pass.

### WAL sidecar bypassed Merkle integrity entirely
**High · Fixed** · `clawhdf5-agent/src/lib.rs`, `wal.rs`

`HDF5Memory::open` verifies the `.h5`'s content Merkle root, then unconditionally replays the companion `.h5.wal` file into the same cache. The WAL had no integrity protection at all — a forged Save or Tombstone entry appended to the sidecar was accepted with zero error, then laundered into a fresh, valid root on the next flush.

**Fix:** WAL format v2 chains a SHA-256 hash across entries. A complete entry whose hash doesn't match is rejected; ordinary crash-mid-write truncation stays silently tolerated, as before. Disclosed limitation: this is an unkeyed hash — it stops a naive tamperer, not one who recomputes the chain, the same class of gap unsigned Merkle data has generally.

### Harness T4b: "detected" was a hash-inequality tautology
**Critical · Fixed** · `clawhdf5-attack-harness/src/attacks.rs`

The selective-chunk-rollback attack asserted only `rolled_back_leaf != committed_leaf` — true for any two distinct hash inputs, regardless of whether any real detection mechanism exists. `compute_leaf_hash`'s version-binding isn't wired into any public `verify_*` API, so this attack never exercised anything real.

**Fix:** Rewritten to honestly report `detected: false` with a root cause explaining both the missing wiring and the tautology in the prior check.

### No verification on the production agent write/read path
**Critical · Fixed** · `clawhdf5-agent/src/storage.rs`, `schema.rs`

The harness proved the Merkle primitives detect tampering — by building the Merkle state itself and calling verifiers directly. Nothing on the actual `write_to_disk` → `read_from_disk` path computed a root or verified one; a tampered on-disk memory file loaded without complaint.

**Fix:** New `integrity` module (on by default) computes a Merkle root over `/memory`, `/sessions`, and `/knowledge_graph` on write and re-verifies on read, fail-closed. `open_strict` additionally rejects a stripped attribute for callers that need it.

### Directed companion-node forgery defeats verify_root (unsigned)
**Medium · Fixed** · `clawhdf5-format/src/merkle.rs` — `verify_root`

The harness's T1b credited unconditional detection to a companion-node tamper. But `verify_root` on unsigned data only checks self-consistency (`companion_hash == SHA-256(nodes)`) — a directed attacker who recomputes the hash over tampered nodes walks straight through. Proven empirically with a throwaway test before writing the fix.

**Fix:** New harness attacks T1d (unsigned, honestly undetected-by-design) and T1f (signed counterpart, detected via the new `verify_signed_root`) make the unsigned/signed boundary explicit instead of overclaiming.

### Signing never wired into the Merkle verify flow
**Medium · Fixed** · `clawhdf5-format/src/merkle.rs` — new `verify_signed_root`

The P2.1 hybrid Ed25519+ML-DSA-65 signer existed and worked, but nothing in `clawhdf5-format`'s verification flow ever checked it — so an algorithm downgrade or companion forgery against a nominally-signed dataset was exactly as unprotected as unsigned data.

**Fix:** New `SignedRootVerifier` trait + `verify_signed_root`, dependency-injected to avoid a format→sign cycle. Harness T6c/T1f prove signed datasets now defeat the algorithm-downgrade and companion-forgery attacks the unsigned path can't.

### Unbounded recursion in B-tree v1 chunk-index traversal
**High · Fixed** · `clawhdf5-format/src/chunked_read.rs` — `collect_chunk_info`

No depth counter, no cycle detection — unlike the structurally identical group B-tree traversal, which already guards at depth 64. A crafted internal node whose child address points back at itself recurses forever and stack-overflow-aborts the process: an unrecoverable crash from an ordinary read of a malicious file, not a catchable error.

**Fix:** Same public-wrapper / private-depth-tracking pattern as the existing group-traversal guard, so the public API is unchanged. New test proves a self-referencing node is now rejected cleanly.

### Unchecked offset+N bounds checks (4 sites)
**Medium · Fixed** · `btree_v1.rs`, `local_heap.rs`, `symbol_table.rs`, `chunked_read.rs`

Four parsers used plain `offset + N > len` instead of `checked_add`, even though the `read_offset` helper defined in each of those same files already gets this right. A crafted address field near `usize::MAX` overflows the addition — panics in debug, wraps and spuriously passes the check in release, then panics on the subsequent slice.

**Fix:** All four switched to `checked_add`, matching the existing helper's pattern.

### norms / activation_weights excluded from the integrity root
**Medium · Fixed** · `clawhdf5-agent/src/schema.rs`, `integrity.rs`

Excluded on the stated premise that they're "recomputed on read" — false: `activation_weights` only defaults when absent, and a genuine independent bug (`n.len() == n.len()`, comparing a value to itself, always true) meant `norms` never actually recomputed on a length mismatch either. Both fields feed recall scoring directly.

**Fix:** Fixed the tautological guard to compare against the real entry count; added both fields to the memory leaf so tampering either is now detected.

### Shift-overflow in fractal heap doubling-table sizing
**Low · Fixed** · `clawhdf5-format/src/fractal_heap.rs` — `block_size_for_row`

`current_rows_in_root_indirect_block` is a raw, unvalidated u16; once the row count reaches 66, `1u64 << (row - 1)` overflows the shift, panicking in debug builds.

**Fix:** `checked_shl` + saturating multiply/add — a degenerate row count now saturates to a safe sentinel instead of panicking.

### T3's "detected" rests on a hardcoded mock signature verifier
**High · Disclosed** · `clawhdf5-attack-harness/src/attacks.rs` — `t3_provenance_forgery`

The control flow under test is real — `select_restore_record` is genuinely production-wired. But every `SignatureVerifier` implementation outside test modules is a toy mock; `clawhdf5-agent` doesn't even depend on `clawhdf5-sign`. T3=yes says nothing about whether a real forged signature would be caught, because nothing in production ever checks one.

**Resolution:** Documentation-only: added an explicit scope disclosure so the green checkmark isn't misread as an operational production defense.

### Signed-path detections aren't reachable from any real file
**Medium · Disclosed** · `clawhdf5-attack-harness/src/attacks.rs` — T5, T1f, T6c

These three genuinely exercise real Ed25519+ML-DSA-65 crypto, not mocks. But `clawhdf5-agent` has no dependency on `clawhdf5-sign`, so no production dataset writer ever produces a signature — every real ClawHDF5 file lands on the unsigned (T1d/T6b) side of the fence, never the green signed side.

**Resolution:** Documentation-only: disclosed that these rows describe a library capability, not a protection any current deployment benefits from.

### Default open() fails open on a stripped integrity root
**Medium · By design** · `clawhdf5-agent/src/storage.rs` — `read_from_disk` (non-strict)

An attacker who deletes the `_merkle_root` attribute (rather than corrupting it) gets a silent, unverified load under the default `open()`. This is the exact tradeoff `open_strict` exists to close — already implemented and documented in this same engagement, not a gap discovered afterward.

**Resolution:** Left as designed: changing the default to fail-closed would reject every pre-existing file lacking the attribute, a bigger behavioral change than this engagement's scope. Flagged here so integrators who need the guarantee know to call `open_strict`.

## Open items

**Signing and encryption remain unreachable from clawhdf5-agent.** `clawhdf5-agent` has no dependency on `clawhdf5-sign`; every real ClawHDF5 file is unsigned and unencrypted today. Per the S2-D2 research plan, production adoption of these primitives is explicitly out of scope for this repo — the Rust implementation feeds a design document for the real C library. Wiring it in for real is a legitimate future ask, not an oversight this engagement silently left unfixed.

**Default `open()` stays fail-open on a missing integrity attribute.** Deliberate backward-compatibility choice — `open_strict` is available for callers that can guarantee every file they load is integrity-protected.

## Addendum, 2026-10-16: T4b is now detected

The matrix above lists T4b (selective per-chunk rollback) as undetected because no `verify_*` API checked the version bound into the leaf preimage. That no longer holds. `verify_chunk` and `verify_dataset` gained it through `Dataset::leaf_hash_for`, and subset verification through `LeafBinding` / `verify_subset_leaves` (`9120fb7`).

T4b now commits a dataset the way the filter pipeline does (`compute_leaf_hash(k, ciphertext, v_k)` leaves, `LeafFormat::Bound` recorded), rolls one chunk's ciphertext and version back together to a prior state that still decrypts, and runs the result through all three verifiers. It counts as detected only if each verifier rejects the rollback **and** accepts the untampered dataset, so the original tautology cannot recur.

Rerun on the synthetic datasets: T4b detected; every other attack's verdict unchanged; 0 of 29 untampered verifications wrongly rejected. The matrix is now 30 of 33 detected. The three remaining undetected attacks (T1d, T6b, T8) and their reasons are unchanged.
